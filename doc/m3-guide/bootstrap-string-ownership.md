This is an implementation reference for the package-private `java.lang.M3StringOwner`, `M3StringAtom`, `M3StringPool` and `M3StringTuple` in `java.base`, plus the descriptor/admission boundary of `M3String`. These are not public application APIs, a new package, a separate Maven module, or a substitute for the public `java.lang.String` contract.

The reviewed public source snapshot is `ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2`. Source review is not matched-runtime acceptance. Builds, tests, recipes, policy checks and resource measurements were **NOT_RUN** for this documentation pass.

## Descriptor, coordinates and retention

`M3String` has exactly two instance fields: `owner` and `value`. The high 32 bits of `value` hold the UTF-16 start; the low 32 bits hold the UTF-16 length. Indexes and lengths are code units, not bytes or Unicode code points. A valid descriptor refers to a range inside one owner; it does not own a text array. The owner can be a native/mapped atom or a tuple retaining two child descriptors. See [M3String 41–86](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3String.java#L41-L86).

A nonempty `slice` shares its owner. Consequently, a small slice can keep an entire large native atom or tuple graph alive. Slicing a tuple does not prune the retained graph. A partial tuple is treated as a height-zero leaf by balancing, which describes the composition algorithm rather than retained-memory size. Empty descriptors use the shared empty owner; a slice of the entire descriptor returns that same descriptor.

### Activation and admission entry points

`System` activates M3 storage after module-system initialization when storage was requested. Ordinary String constructor helpers separately require the enabled flag, a booted VM, `admissionEnabled()` and nonempty input. `String.m3()` is a field read; it is not a general lazy-admission operation. The JNI-specific `ensureM3()` path can attach a descriptor, and `m3AdmitNative` returns the compatibility sentinel only after successful admission. A refusal leaves the caller's flat path available. See the pinned [System boundary](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/System.java#L2235-L2242) and [String boundary](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/String.java#L5556-L5642).

## Atom storage and trusted factory contracts

`M3StringAtom` stores an immutable spelling at `address`, with `storageWidth` one or two and explicit `bigEndian`. Width one reads unsigned Latin1 units. Local width-two payloads are written big-endian. Mapped payloads can have another physical byte order. **Logical String coder and physical width differ:** a width-two mapped row containing only Latin1 units can advertise the LATIN1 coder when compact strings are enabled.

`payloadOwner` retains mapped ownership; VM-local native blocks instead have pool-owned release metadata. `canonicalId` is owner metadata, not a portable identifier. `UNSAFE` is the native access mechanism. None of the ordinary copying factories retains its source byte[], char[] or int[]. Callers must keep mutable input stable through validation, hashing, comparison and copying; the implementation is not a transaction over concurrently changed input. See [M3StringAtom 17–45](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringAtom.java#L17-L45).

These are trusted runtime operations, **not a safe general pointer-import API**. The constructor checks nonzero address for a nonempty atom and width in {1,2}; it does not independently prove address validity, allocation extent, positive length, coder/hash consistency, immutability or lifetime. In particular, `localCodePoints` relies on the pool's previously derived UTF-16 length/coder; its post-write mismatch check is not a substitute for those preconditions.

## Pool admission, exact reuse and resource refusal

`M3StringPool` is static-only; its private no-argument constructor is intentionally empty. Scalar admissions validate source/range/coder, return `EMPTY` for valid empty input, determine compactness/size, try the active lexicon, then route local candidates by `(coder, byteLength, hash64)`. A local candidate is reused only after exact content comparison. The private `Fingerprint` record's components `coder`, `byteLength` and `hash64` are candidate-routing keys; the generated record equality/hash/accessors do not prove String equality. See [M3StringPool 771–771](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringPool.java#L771-L771).

For local misses, the pool drains stale references, synchronizes the selected bucket, rechecks exact candidates and reserves native bytes before allocating. A slow-path reservation is returned if another thread has published an exact hit in the meantime. This preserves reuse while allowing an ordinary admission to return null when the configured budget cannot be reserved. It does not promise constant-time admission, lock-free progress, or bounded total process memory.

## Tuple composition: layout identity is not text equality

`concat(left,right)` first requires nonnull descriptors; empty operands are identities. It rejects a combined logical length above `Integer.MAX_VALUE` with `OutOfMemoryError("Required length exceeds implementation limit")` before coalescing or tuple arithmetic. Adjacent ranges of the **same owner object** coalesce into a single range. Other inputs enter balanced persistent composition. See [M3StringPool 483–499](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringPool.java#L483-L499).

A tuple's Java hash is `leftHash * 31^rightLength + rightHash` with intentional wrapping `int` arithmetic. Its coder is the bitwise union of child coders. Balancing uses only whole-tuple heights; partial tuple descriptors count as leaves. Reassociation preserves ordered content/coordinates without flattening text.

Canonical lookup first chooses a route bucket using Java hash, total length, coder and up to four leading/trailing units. The route is candidate-only. `sameLeafSequence` then compares the **normalized ordered sequence of terminal atom object, start and length**. `LeafCursor` merges adjacent terminal ranges of the same atom. Equivalent parenthesizations can reuse one registered owner; equal UTF-16 text represented with a different terminal-owner/range decomposition need not reuse it.

When tuple registration is full, composition still returns a new tuple without installing its weak lookup entry. Existing entries can still be reused. Therefore unconditional same-owner convergence is not promised, even for otherwise equivalent layouts. This cap changes reuse, not the public content semantics.

## Lexicon snapshot, formats and mapped lifetime

`initializeLexicon(String)` ignores null/empty filenames and an already installed lexicon. Otherwise it takes the pool class lock and opens once. A caught `IOException` or `RuntimeException` installs `Lexicon.unavailable()` and calls `reportLexiconFailure` at most once per VM. If `System.err` is absent, the report flag is still set. Later calls do not automatically retry. The boundary does not swallow every `Error`, including allocation failures. `lexicon` is volatile; `lexiconFailureReported` is guarded by the class lock. See [M3StringPool 84–114](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringPool.java#L84-L114).

The `FileChannel` closes after read-only mapping; the mapping stays retained by the lexicon and mapped atoms. A read-only mapping does **not** stop another process from rewriting/truncating the file. The input must satisfy the existing trusted-directory, immutable committed-bytes publication contract. There is no close/unmap API here and no cross-process universal interning service.

| Input | Accepted/validated interpretation |
| --- | --- |
| `M3LEX001`, versions 1 or 2 | Whole image 64 bytes through 1 GiB; dimensions, directory widths, payload size, SHA-256, row bounds, exact Java hashes and strict UTF-16 row ordering checked. Header/directory numeric reads are big-endian; payload units are **little-endian**. Version 1 derives hashes; version 2 validates stored hashes. The digest covers bytes 0–31 and bytes from offset 64 onward, excluding the stored digest slot. |
| `SYNARR01`, version 1 | Validates header CRC and bounds, record structure/size, record CRC/commit marker, permitted width/language shape and referenced prior scalar ranges for tuple records. The ordinary String lookup includes only **nonempty language-0 width-two scalar records**, with **big-endian UTF-16** payload and checked Java hashes. Byte records, other languages and persisted tuples do not become independent String lexicon atoms. Accepted scalar rows are sorted for lookup; this route does not impose M3LEX's strict duplicate-row rejection. |

These statements describe the implemented checks, not complete validation of every field or a hostile-storage security proof. `LEXICON_MAGIC`, `LEXICON_HEADER` (64) and `MAX_LEXICON_BYTES` (1 GiB) delimit the first loader; the shared-arena path additionally caps each record payload at 64 MiB. Mapped misses remain local admissions and never append to the file. The snapshot does not dynamically incorporate later appends.

`Lexicon.atom(row)` lazily caches a mapped atom for a validated lookup row. Its ID combines a high-bit marker, masked generation bits and row+1; M3LEX generation is derived from its digest and shared-arena generation from namespace values. These numeric IDs are not portable source IDs, file-record identities or proof that arbitrary equal text has the same owner. `namespaceHigh`, `namespaceLow` and `recordOffsets` preserve shared-arena metadata but are not exposed as a universal application coordinate API. See [M3StringPool 1191–1288](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringPool.java#L1191-L1288).

## Owner-local facts and publication

`M3StringOwner` is sealed to atoms and tuples. `ATOM`/`TUPLE` tag `kind`; `length`, `coder`, `javaHash` and `structuralHash64` describe that owner. Its constructor stores these trusted values without full semantic validation. The volatile `facts` field holds whole-owner facts. Four volatile slots, `range0`, `range1`, `range2` and `range3`, hold exact packed-coordinate `RangeFact` entries. They do not own canonical spelling arrays. See [M3StringOwner 10–37](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringOwner.java#L10-L37).

Whole facts initialize under the owner monitor and validate UTF-16 length and Java hash before volatile publication; mismatch throws `InternalError`. Range facts compute outside that monitor, so concurrent misses may duplicate computation. Publication rechecks for an existing exact coordinate, shifts the four slots on insertion and inserts at the front. **Hits do not move slots: this is not LRU.** Cache scope includes the particular owner; equal numeric coordinates on another owner do not authorize reuse. See [M3StringOwner 19–129](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/classes/java/lang/M3StringOwner.java#L19-L129).

`rangeFacts(coordinate,value)` is trusted: a hit can return before checking `value`, and a miss uses the supplied descriptor's start/length without independently proving it belongs to this owner or matches the supplied packed key. Normal `M3String.facts()` supplies that relationship. Do not expose this method as an authentication or general cache-import API.

## Failure and identity checklist

| Situation | Observable internal disposition |
| --- | --- |
| Ordinary scalar budget cannot be reserved | Null admission; callers retain their documented flat fallback. This is not the native allocator's failure path. |
| Dedicated `internUnit` budget pressure | No configured-budget refusal; accounting may exceed `MAX_LOCAL_BYTES`. |
| Tuple registration cap reached | New valid composition returned without registration; no null refusal. |
| Null source or invalid source/destination bounds | `NullPointerException` / index-bounds exception at the checked entry point; trusted helpers have explicitly narrower validation and shortcut behavior. |
| Invalid scalar coder, malformed whole compact payload or invalid code point | `IllegalArgumentException` at the corresponding pool boundary; comparison helpers may return false instead as documented. |
| Too-large scalar UTF16 allocation shape or combined concat length | `OutOfMemoryError` size failure, distinct from configured-budget null refusal. |
| Native/heap allocation failure | Can still throw; this documentation does not certify every failure path or GC/native-release race. |
| Canonical fact mismatch / derived code-point length mismatch | `InternalError`; invariant failure, not ordinary absence. |
| ID sequence nonpositive | `IllegalStateException` from `nextId`. |
| Caught lexicon open/validation failure | One unavailable sentinel and at most one diagnostic; local/flat fallback remains available. Uncaught `Error` is not converted to this diagnostic-only mode. |
| Equal route/Java hash or numeric IDs | Candidate metadata only; exact content or exact owner/range comparison remains necessary for its specific operation. |

The VM's [field-offset schema and recursive native range copying](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/hotspot/share/classfile/javaClasses.cpp#L945-L1071) match these descriptor/owner/atom/tuple fields. [String.c shadow entry points](https://github.com/hsoliwal/M3jdk21/blob/ed53dc8ab4fb6fd93ad1ed0c762546bdda475bb2/src/java.base/share/native/libjava/String.c#L51-L131) allocate genuine final Java byte/char arrays for the explicit compatibility-shadow boundary and fill them through owner-backed readers. This does not mean every encoded output array elsewhere in String is allocated by JNI. Native array shadows and acquire/release pointers never replace canonical ownership.
