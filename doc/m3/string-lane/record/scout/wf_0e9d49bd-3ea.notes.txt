RUNNERS-UP (not in the six)
- toLowerCase / toUpperCase facts gate: M3String.caseMap 1616-1630 scans with a cursor until the first change. For a value with prepared facts, ascii == true and (regexAnyClasses & REGEX_UPPER) == 0 (REGEX_LOWER for toUpperCase) proves no unit changes, so 'return this' in O(1); exact because the scan at 1623-1629 is locale independent and for ASCII only A-Z (a-z) change. Small, certain; confidence 0.8.
- charAt finger: a String backed by a tuple re-descends the DAG on every charAt (M3StringTuple 34-39). A single cached leaf window on the root tuple (immutable holder, racy publish like String.hash) would make sequential charAt O(1) amortized for every caller including Matcher, Integer.parseInt and user loops. Costs one reference per tuple and a holder per leaf switch; needs a benchmark; confidence 0.45.
- Atom bulk primitives: M3StringAtom.getBytes / getChars copy byte by byte through Unsafe (434-503). Same-width copies could use Unsafe.copyMemory, opposite byte order copySwapMemory. Every window path (facts scan, searches, encode, builder append) sits on this. Whether C2 already vectorizes these loops is not verified.

How the builders use M3 today (from the code):
- M3StringBuilderLane holds four parallel arrays (text String[], span long[] = start<<32 | length, flatAt int[], logicalEnd int[]), units, virtualCapacity, one state bit and a composed cache keyed on (flatCount, pieces). There are no per-piece objects and no rope builder; the flat chunks stay in the builder's own value/count, in order.
- A String is lifted as a piece only when M3 storage is on, the range is at least 64 units and at least 1/8 of its source, s.m3() != null, the VM is booted and admission is enabled (lane lines 74-82). Everything else is copied into the flat buffer through String.getBytes, which uses the leaf path and does not materialize the argument.
- Lane-aware without flatten: length, capacity, ensureCapacity, charAt, codePointAt, codePointBefore, append(String), append(String range), all flat-tail appends, indexOf/lastIndexOf, toString, getBytes (copyOut). Lane-aware by rebuilding the lane: setCharAt, delete, deleteCharAt, replace, insert(String) and the valueOf-based inserts, reverse. Full copy without detaching: chars, codePoints, the peer side of compareTo, append(AbstractStringBuilder).
- Flatten (m3EnsureFlat): compareTo (this side), trimToSize, setLength, codePointCount, offsetByCodePoints, getChars, both substring forms, subSequence, insert(char[]) (two forms), insert(CharSequence) (two forms), insert(int,char), append of a non-String CharSequence range, repeat of a foreign CharSequence, mix, prepend, getValue (new String(sb), contentEquals), writeObject.
- toString: without a lane it is new String(this) -> getValue -> maybeAdmitCompact, a one-atom admission of the flat content (String.java 5429-5444); the String keeps only the shared empty sentinel as value. With a lane, compose admits each flat chunk as an atom, takes an O(1) slice per piece and folds pairs into a balanced tuple; it returns null (flat fallback, which flattens) when admission is off, a piece is not M3-backed or the pool refuses. StringBuffer keeps the composed String in toStringCache.
