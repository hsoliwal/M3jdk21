# P1: real String singleton-join backing reuse

Original experiment contributions: Hitesh Soliwal <hsoliwal@gmail.com>.
The new harness/recipe files are Apache-2.0. The changed OpenJDK String source
retains its original GPLv2 with Classpath Exception notices and terms.

This stage changes the actual `java.lang.String.join` implementation in a built
OpenJDK image. With one element and empty prefix/suffix, it constructs a fresh
String over that element's already immutable `byte[]` and coder, avoiding a
second payload allocation/copy. The result object remains distinct, hash state
starts at its normal default, and VM dedup flags are initialized normally.
The input backing is already a complete String array, so this introduces no
subrange retention. Empty, null-converted, LATIN1 and UTF16 contents work through
the same existing representation. The public conversion/iteration callbacks
still run before this internal helper. Multiple elements or nonempty affixes
retain the original checked-length flattening path.

This is a new reuse site, not a claim to have invented String(String)'s existing
backing sharing. No cache, pool, optional initializer, constructor hook, new
String field, public API, VM opcode or intrinsic is introduced. No claim of
transparent discontiguous String support is made. HotSpot source is unchanged;
its current layout contracts are checked by the recipe and exercised by tests.

## Replay and rollback

The base is foundation commit `500201945636cae6319ae3513a251fabdd119f62` on
official jdk-21+35 `890adb6410dab4606a4f26a942aed02fb2f55387`.

```
python3 m3/runtime-stage1/apply.py --check
python3 m3/runtime-stage1/test_recipe.py
python3 m3/runtime-stage1/apply.py --target /path/to/isolate
```

The recipe verifies String pre/post hashes, the insertion, and 18 unchanged
runtime source files before its one atomic file replacement. It accepts exact
postimages idempotently and refuses drift or a symlink String destination.
`--reverse` restores the exact original source after checking the same fences.
This is a recipe for the runtime edit, not a package manager for the harness.
The complete patch is also supplied as `String.patch`.

P0's source guards are intentionally unchanged. P1's recipe tests verify the
historic P0 recipe and tests on a temporary reversed runtime snapshot; P0 is not
run directly against the patched String. No safety guard is bypassed.

Before building, preserve the baseline image outside the build tree. Use the
private boot JDK and isolated native dependencies described in
`../docs/native-build.md`, then `make images JOBS=5`. Run only the selected image
by absolute path or explicit JAVA_HOME/PATH. Roll back execution by selecting
the preserved original Java; do not overwrite an installed JDK or transplant
String.class into a different runtime. CDS archives are regenerated by images.

## Verification

```
M3_BASE_JDK=/path/to/original M3_TEST_JDK=/path/to/patched \
  bash m3/runtime-stage1/run-focused.sh
```

The focused checks cover every UTF16 code unit, malformed surrogate sequences,
embedded NUL, hash collisions/zero hashes, intern/result identity, actual backing
identity, callback order, mutable ingress/egress, charset boundaries, public
String.join routes, StringJoiner and joining collectors, non-singleton fallback,
affixes, regex, concurrent publication, and lifetime. Backing identity checks
are disabled in GC stress lanes because dedup may legally replace equal arrays;
semantic and fresh-result checks remain enabled.

The native probe tests GetStringChars, GetStringCritical, GetStringUTFChars,
GetStringRegion, GetStringUTFRegion, NewString and NewStringUTF plus bounds
exceptions under -Xcheck:jni. It copies critical data without allocation or JNI
calls while pinned, releases pointers, and never retains them after release.

`JoinAllocation` measures prepared singleton inputs with separately reported
setup, warmup, operation wall/CPU time and thread allocation. Results escape to
a retained array. Backing identity/payload inspection occurs after timing.
Use fresh JVM forks with equal settings; results are a narrow synthetic test,
not a throughput or application-memory guarantee. GC-assisted dedup and
subsequent lifetime are different measurements.

Proper jtreg runs use the existing OpenJDK test roots and a private jtreg 7.5.2
installation. Build the required native test fixture first (from the repository
root with the same isolated build environment):

```
make build-test-jdk-jtreg-native JOBS=3 \
  BUILD_JDK_JTREG_NATIVE_SRC="$PWD/test/jdk/java/lang/String/nativeEncoding"
```

The runner passes its native library directory to jtreg. `run-jtreg.sh` records String/StringJoiner and HotSpot intrinsic/
stringopts suites on both images plus the four-action focused jtreg test.
The evidence identifies exactly which selections passed or failed. This is not
a full upstream jtreg pass, a cross-platform proof, or a product release.

See `runtime-contracts.md` for the coordinated segmented-layout gate and
`synexia-pin.json` for the established production owners. Local generated
classes, images, downloaded dependencies and raw run output belong in ignored
`m3/build/` or the external results directory, not in source control.
