# Feedback from rebuilt M3JDK images

At head `02ab933680f98ca28b10c151cf61e9fe24cb9200` (tested merge
`a823bf74247b7cf909a81960ebe4ec78ee5e43d6`), both Linux x64 fastdebug images
built successfully. Lane28 and TQ passed their bounded behavior checks in
interpreter, mixed, C1 and C2 modes. Lane28 called the native peer exported by
the built image's own `libjava`; TQ retained its independent test-only JNI oracle.

The compilation logs contain 17 C1 / 18 C2 bit-lane kernels and 10 C1 / 20 C2
TQ kernels. With `UseM3StringStorage`, the VM deliberately switches to
interpreted mode; the C1-requested behavioral runs passed with no compiled
methods. Both workflows then correctly stopped at the old, incompatible
compiled-kernel expectation. No completed seven-mode or whole-program pass is
claimed. C2-requested M3 modes were not reached in these runs.

This separates two optimization tracks. Normal-layout JDK consumers can use
these bounded kernels and retain normal compiler qualification. Alternate
String storage needs separate HotSpot compiler, intrinsic, GC and deoptimization
work before its interpreter guard can be removed. Do not infer M3-enabled JIT
support from normal-layout results.

TQ still reported zero warm payload reads. The earlier cost feedback remains
unchanged: successful native linkage is not a native speedup measurement.
Rank preparation, JNI crossover and sparse zero-fill remain source-owner
optimization priorities. Source and target revisions, run IDs and per-kernel
counts are recorded in the companion JSON. Existing full-reactor/99% coverage,
jtreg/TCK and lifecycle/platform gates remain open.
