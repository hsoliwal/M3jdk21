## Upstream priorities

1. **native-count-routing** (measured): On both warmed C2 forks, cached Java full-range count and Java partial count cost less than the explicit JNI peer on this fixture. Keep cached Java facts as the default; measure workload-specific crossover before adding any automatic native routing or batching. Preserve explicit native verification semantics.
2. **rank-amortization** (measured): First nontrivial rank includes count preparation; subsequent rank/select reuses maintained metadata. Account for preparation and mutation rate when selecting this strategy. Measure sparse/dense and query/write ratios before changing eager/lazy admission.
3. **sparse-zero-fill** (source-review-not-benchmarked): Zero fill checks absent storage once per 4096-slot page; a full empty 28-bit range traverses 65536 page-sized chunks. Benchmark a validated empty-owner shortcut and absent-region skipping. Keep range checks ahead of shortcuts and preserve behavior on allocated pages.
4. **address-arithmetic** (source-review-not-benchmarked): Primitive address/mask helpers have no per-entry allocation. Public checked accessors repeat some validation through private owner paths. Profile compiled code before considering unchecked private kernels; preserve all externally reachable bounds and 28-bit limits.

The JNI result argues for keeping the existing Java default on this fixture;
it does not justify changing the explicit native API into a silent fallback.
No blanket native speedup, inferred hardware crossover or complete-JDK pass is
claimed. The sparse-zero-fill and address opportunities still need measurements.

The port uses the existing Maven/OpenRewrite snapshot engines. Reproduce with
`mvn -f m3/tooling/lane28/pom.xml verify` in its M3JDK candidate; raw cost logs
and `M3Lane28Cost` are retained there. Each future port should emit similarly
revision-bound feedback; both-side source/target edits require reconciliation.
