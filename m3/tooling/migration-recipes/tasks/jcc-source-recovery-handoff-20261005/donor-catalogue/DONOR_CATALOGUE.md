# M3 donor catalogue and observed fixture coverage

This catalogue connects 18 primary references to the existing Synexia recipe, compiler and MIndex owners. It is the documentation follow-up to the implementation and replay changes. It adds category metadata and an evidence map; it adds no dependency, search service, recipe engine or challenge implementation.

The completed donor packet contains **247 literal input pairs and 1,477 regex input pairs per native mode**. All seven donor JUnit tests passed with native mode `off`, and all seven passed again with mode `required`. The main `off` run passed 68 tests overall. The exact corpus, operations, source hashes and log hashes are in [EXECUTED_TEST_MAPPING.md](EXECUTED_TEST_MAPPING.md) and [donor_catalogue.json](donor_catalogue.json).

## Review and lookup order

1. Inventory the existing Synexia owner, its recipe and its fixtures. Record the source revision, public and private interfaces, accepted inputs, indexing, outputs and exceptions before choosing a replacement atom.
2. Consult **existing Synexia → JDK/javac/JLS → OpenRewrite → a specific GitHub donor**, in that order. JDK sources establish Java language and compiler contracts; OpenRewrite sources establish recipe behavior. A GitHub donor must fill a named gap and have a recorded file, revision and license before source adoption.
3. Classify the problem before lookup: literal or pattern grammar; full match or search; first or all occurrences; input alphabet and encoding; index coordinate; empty-input and error behavior. Look up **LeetCode → HackerRank → GeeksforGeeks**. Keep each platform's contract separate, including unavailable statement details.
4. Compare one candidate file or private atom at a time against that contract. A category match nominates a candidate. A text match alone cannot authorize an attributed Java edit. Preserve owner and overload resolution, interface shape, evaluation order and observable exceptions through the existing recipe workflow.
5. Make the reusable Maven/OpenRewrite recipe and bounded fixtures the work product. Reuse `M3RecipeMasteryCombinator` where applicable; declare finite dimensions and expected cardinality. Positive parser refusal is failure. Invalid syntax, unsupported constructs and exhausted limits are separate outcomes.
6. Retain the materialized diff, ordered lint → compile → tests → runtime evidence, and existing replay/fixed-point checks. A passing finite corpus supports its declared domain; it does not prove unrestricted equivalence or universal termination.

## Boundaries retained during comparison

| Comparison | Required distinction |
| --- | --- |
| Literal versus regex | Metacharacters are data in a literal contract. Regex grammar and quoting must be explicit. |
| Whole match versus search | Boolean `matches` and `find` are independently checked. Captures and match positions are outside this regex packet. |
| Regex versus source edit | A string containing code is still test data. Attributed source edits belong to the existing compiler/recipe fixtures. |
| UTF-16 versus UTF-8 | Character indices and byte offsets use independent oracles. Supplementary characters occupy different numbers of units. See [String](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html) and [JNI string operations](https://docs.oracle.com/en/java/javase/21/docs/specs/jni/functions.html#string-operations). |
| Lexical validity versus bracket balance | Java Unicode translation precedes tokenization; use the compiler and [JLS lexical rules](https://docs.oracle.com/javase/specs/jls/se21/html/jls-3.html). |
| Java acceptance versus automaton eligibility | A valid JDK expression may exceed the automaton's supported grammar or resource bounds. Such refusal is not a passed matching case. |
| Same corpus in two modes versus new inputs | `off` and `required` are two executions of the same declared corpus. They do not double its distinct input count. |
