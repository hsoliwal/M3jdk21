# A3 — Atomize, Patternize, Absorb

Status: M3JDK21 tool-plane absorption contract.

## Name

A3 means:

1. Atomize — mechanically split or identify contract-preserving semantic leaves.
2. Patternize — assign an admitted pattern/IOP role and dependency position.
3. Absorb — replay a proven atom into the target JDK lane only after scope and compatibility admission.

The short name is intentional. New M3-only JDK tooling defines a pattern/term once and then uses a short acronym. Do not introduce long framework-style API names into the JDK product.

A3 itself is tooling. It is not a JDK runtime API.

## Build boundary

The OpenJDK build remains authoritative:

    configure -> make -> jtreg -> runtime/benchmark

Maven is a control plane, not a replacement JDK build:

    m3/pom.xml
      -> tooling/migration-recipes
      -> tooling/a3
      -> backport/admission tooling

A3 may read src/ and test/, but it does not make Maven compile the OpenJDK product tree.

## Virtual Mavenization

A3 treats the existing OpenJDK checkout as a virtual Maven corpus without adding POMs to each JDK module.

A3Inv scans the real repository and records:

    tree | module | area | path | kind | bytes | sha256

This inventory is deterministic and content-addressed. It creates module/source coordinates needed by OpenRewrite and A3 without changing OpenJDK build descriptors.

## Public A3 tool names

- A3Inv — inventory the JDK source/test corpus.
- A3Alg — validate tri-platform algorithm evidence and license-bound GitHub lineage.
- A3Plan — preserve and join the JEP/JBS/community/algorithm admission catalogues.
- A3Apply — apply the retained FILE-local Java convergence DAG to explicitly selected files.
- A3 — compact CLI.

Generated evidence lives under m3/build/a3/.

## NRW — no root writes

A3Apply accepts only explicit Java files under src/ or test/. It never overwrites those files.

For every selected file it writes:

    m3/build/a3/<run>/candidate/<original path>
    m3/build/a3/<run>/receipt.tsv

The receipt binds source path, exact recipe, FILE scope, before SHA-256, after SHA-256, changed flag and fixed-point proof. An output path outside m3/build/ is rejected. Canonical JDK promotion remains a later explicit step.

## Recipe reuse

A3 does not invent a second atomization engine. A3Apply reuses com.m3.rewrite.M3Java21ConvergenceRecipe.

The retained DAG remains:

    inventory
      -> atomize
      -> patternize / IOP
      -> document
      -> fixed point

A3 applies it one explicit file at a time and executes it again in memory. A candidate is not written unless the second execution is a zero-change fixed point.

## All-JEP and enhancement planning

A3Plan reads all current rows from:

- m3/backports/JEP_CATALOGUE.tsv
- m3/backports/UPSTREAM_CHANGE_SEEDS.tsv
- m3/backports/COMMUNITY_CAPABILITY_CANDIDATES.tsv

It preserves every original disposition and adds an A3 lane:

| Existing disposition | A3 lane | Meaning |
| --- | --- | --- |
| admitted | ADMIT | already admitted; reconcile proof/current tree |
| candidate-adapted | ADAPT | Java-21 adaptation exists; close proof |
| candidate | DIRECT | recipe/packet candidate |
| candidate-high-risk | SYSTEM | VM/native/multi-module dependency closure required |
| hold-* | HOLD | dependency/preview/compat review |
| superseded* | LINEAGE | follow later/final lineage |
| reject-* | BLOCK | current compatibility contract blocks direct absorption |
| other/pending pack status | REVIEW | evidence/admission work remains |

Therefore all catalogue rows participate in the absorption plan, including blocked and superseded rows. Plan all does not mean silently backport all.

## Algorithm evidence bridge

A3Alg validates m3/backports/ALGORITHM_CATALOGUE.tsv before algorithm shapes enter planning.
LeetCode, HackerRank and GeeksforGeeks are reference-only taxonomy/constraint sources. Their
solution/editorial code is never copied into OpenJDK. GitHub implementation lineage is separately
license-bound and may be JDK-owned, permissively adapted, or reference-only.

Strict admitted/candidate rows require all three challenge-platform references. Incomplete evidence
remains hold/review work. A3Plan joins validated rows as ALG work without granting mutation or
promotion authority.

## Absorption flow

    A3Inv
      -> identify touched JDK modules/files
      -> compare upstream/source-sealed donor packet
      -> run FILE atomization/patternization where contract-preserving
      -> classify cross-file remainder by scope
      -> produce recipe crate / DAG
      -> candidate replay against current master preimages
      -> fixed point
      -> native OpenJDK build
      -> focused jtreg
      -> runtime/benchmark where relevant
      -> serial promotion

Atomization is preparation, not authority. A JEP that changes grammar, public API, VM layout, JNI, GC, JIT, serviceability or module contracts still requires the corresponding wider scope.

## Donor policy

Donor evidence is inventory-first. Priority:

1. OpenJDK current and later release lineage.
2. Existing M3JDK21/Synexia retained atoms and recipes.
3. Apache/Spring/other upstream implementations when relevant to tooling patterns.
4. LeetCode, HackerRank, GeeksforGeeks and similar catalogues for algorithm taxonomy, known complexity classes, edge cases and benchmark ideas.

Competitive-programming code is not copied into the JDK. A selected algorithm is independently reimplemented as a JDK-owned atom and must pass JDK contract/equivalence tests, complexity/benchmark comparison, license/provenance evidence, and native/JIT/GC/JNI proof when those boundaries are crossed.

## JNI and native code

OpenRewrite covers Java structure. JNI/HotSpot/native absorption stays in the same A3 plan but uses native-aware deterministic transformers or source-sealed replay when OpenRewrite is not the truthful parser.

The first native bridge is documented in [A3 native/JNI file atoms](a3-native-jni.md). Native
deltas are classified separately and can be emitted as one-file hash-pinned source-sealed recipe
atoms with `--include-native --crate-size 1`. That byte-custody lane is preparation only; deeper
function-level native atomization requires a truthful C/C++ parser such as admitted clang tooling.

The Java/native join is never FILE-local merely because each side can be edited separately. JNI signature, layout, lifetime, GC, safepoint and error semantics determine actual authority.

## Completion rule

A3 makes absorption easier; it does not lower the completion bar.

Do not call a JEP/subsystem absorbed until inventory is complete, recipe/source lineage is pinned, atom/pattern evidence is complete, scope is admitted, current-master replay reaches fixed point, OpenJDK build is green, focused jtreg is green, and runtime/benchmark proof passes where required.

The compiler/runtime remain the oracle.


## Official OpenRewrite composition contract

A3 follows the OpenRewrite authoring split rather than treating every recipe DAG as new Java code.

- Proven leaf transformations remain imperative Java recipes because they own semantic LST logic.
- Composition of those already-proven leaves is declarative YAML under `META-INF/rewrite`.
- A3 activates the named declarative recipe through OpenRewrite `Environment`.
- Whole-corpus inventory that must inspect all sources before mutation belongs in scanning/inventory
  stages; FILE mutation remains one source at a time.
- Declarative recipe behavior is tested from resources with OpenRewrite `RewriteTest`.
- The previous `M3Java21ConvergenceRecipe` Java composite is retained as a compatibility oracle,
  not the primary A3 composition mechanism.

Canonical declarative entry point:

```text
com.m3.rewrite.M3Java21Convergence
  -> M3InventoryPureIntAtomCandidates
  -> M3AtomizePureIntReturnRecipe
  -> M3PatternizePureIntAtomRecipe
  -> M3DocumentPureIntAtomRecipe
```

The order is deliberate and source-compatible with the retained Java composite. Adding another
semantic family requires its own bounded leaf proof before it may be appended to this declarative
DAG.

The Maven/OpenRewrite plane remains tooling only. OpenJDK product acceptance still requires the
native `configure -> make -> jtreg -> runtime` oracle.
