## Scope and reuse

Reuse native Git for graph traversal and binary-capable exact patches, Python's
standard library for records, and the existing standalone Maven exec-plugin
convention for recipe invocation. Do not build another parser/refactoring engine.
The existing `m3/migration`, `m3/tooling`, foundation recipes and name-mapping
remain their respective authorities. This module supplies PSE/CCPS evidence to
those owners; it does not replace their scanners, recipes or mapping schema.

`git_graph.py` owns immutable Git-object reads and NUL-safe raw-diff decoding.
`audit.py` owns deterministic graph reduction and evidence publication.
`test_audit.py` owns synthetic repository contract tests.
`snapshot.json` owns the frozen upstream/candidate/target/ref boundary.
`ATOM_PLAN.tsv` records proposed semantic work and coupled promotion boundaries.
These are cohesive responsibilities, not arbitrary tiny-method extraction.

## Execution

Python 3.10+ and Git are required. Run from a complete local clone; the output
must be a new directory outside both the worktree and Git administration paths:

```sh
python3 -B -m unittest discover -s m3/history -p 'test_*.py' -v
python3 -B m3/history/audit.py --repo . --snapshot m3/history/snapshot.json --output /tmp/m3-history-audit
```

The default snapshot is immutable. It intentionally does not follow a moving
master or branch name. Missing commits, shallow history, unrelated roots,
pre-existing outputs, source-local outputs and budget overruns are refused.
Cancellation propagates between Git subprocesses; each subprocess has a timeout.
There is no apply/merge/reset/rebase/delete mode and no worker writes to canon.
Do not run against a concurrently modified object database; the tool detects ref
movement but cannot make noncooperating writers transactional.

The Maven entry point reuses exec-maven-plugin 3.6.4 already used by
`m3/migration/pom.xml`, without making Maven an OpenJDK bootstrap dependency:

```sh
mvn -f m3/history/pom.xml verify -Dm3.repo=/absolute/clone -Dm3.output=/tmp/m3-history-audit
```

Maven acceptance must be recorded separately from direct Python execution.

## Reverse and forward passes

1. Validate full object IDs and the common upstream boundary. Freeze the set of
   branch tips from the snapshot, not timestamps and not a recent-search limit.
2. Collect the union of reachable commits excluding upstream ancestry. Order
   parents before children with a SHA-tiebroken topological sort; the reverse
   ledger is the exact reversed sequence. Side branches older than the candidate
   remain visible, because time filtering would lose their later-merged work.
3. Inspect **every parent edge**, including all octopus parents. Record full
   old/new modes and object IDs, status, path, and SHA-256-addressed binary-capable
   patch. Never substitute a combined merge diff or first-parent-only traversal.
4. Flag first-parent-tree reuse with different side-parent trees as a review
   obligation, not an automatic accusation or semantic-equivalence conclusion.
5. Compare candidate and target trees at every fork-touched path. Emit exact
   equality, missing content or different-content review, not an automatic merge.
6. Hash changed blobs once and reuse the facts. Exact clusters are proposals;
   normalized/semantic clustering is explicitly not performed by this tool.
7. Emit ledgers, coverage limits and a digest of all artifacts. Ref movement,
   incomplete reads or output-budget failures leave an INCOMPLETE marker and no
   complete audit receipt. Restart uses a fresh output; existing output is never
   overwritten or silently treated as a successful checkpoint.

Git references: `git rev-list`, `git diff-tree`, `git cat-file` and `git ls-tree`.
The command log and implementation digest are part of each run's provenance.
Mechanical traversal coverage is not semantic review, compile success, test
success or runtime acceptance. `FINAL_REPORT.md` explicitly keeps these separate.
The optional PR collector records current PR #1..#17 metadata as a separately
captured witness. A PR head outside the frozen branch snapshot is a coverage gap,
not silently folded into an earlier snapshot.

## Retained-capability audit

Merged history is evidence, not proof that a capability remains in the current tree. The
`retention.py` pass closes that gap for capabilities explicitly listed in
`RETAINED_CAPABILITIES.tsv`.

Each catalogue row points to an existing source-sealed recipe manifest. For an exact Git commit the
audit reads both catalogue and manifests from Git objects, hashes the current target blobs, and
emits one of:

- `RETAINED_EXACT` — the current blob still equals the sealed postimage;
- `PRESENT_DRIFTED_REVIEW` — the path remains but evolved after the sealed postimage;
- `MISSING` — a retained target disappeared from the current tree.

Drift is a review obligation, not automatic semantic loss. Missing retained targets are a failing
audit result when `--require-no-missing` is requested. The baseline extension described below also
refuses deleted or incompatible declarations; rewriting the expected hash cannot erase a prior
obligation.

The initial retained contract covers both JEP 458 source-sealed graphs. New compatible capabilities
are added to the retention catalogue only after their product packet is actually promoted; candidate
PRs are never pre-declared as retained.

Maven/CI entry point:

```sh
mvn -B -f m3/history/retention-pom.xml verify \
  -Dm3.repo=/absolute/full-clone \
  -Dm3.retentionCommit=<full-commit-id> \
  -Dm3.output=/outside-worktree/retention
```

This audit is read-only. It does not restore, merge, cherry-pick or infer behavioral equivalence.

### Immutable baseline and all-parent retention

The Python API keeps the original three-argument behavior and complete summary/root:
`inspect(repo, commit, catalogue)`. Existing callers do not acquire an implicit baseline.
The extension is opt-in with keyword-only `baseline_commits=(full_id, ...)` and
`include_parents=True`. The tuple contains full lowercase Git commit IDs; duplicate explicit
IDs, abbreviations, moving refs, tree IDs and malformed IDs refuse. Baseline order does not change
the resulting report. `include_parents` includes every direct parent, including all octopus parents.

Each baseline's catalogue and manifests are read from that baseline's own exact Git commit.
The candidate's catalogue cannot remove inherited obligations by dropping a capability row,
moving/deleting a manifest, deleting a target row, or changing its expected SHA-256. All distinct
expectations survive in the report with their sorted source-commit provenance. Conflicting hashes
and manifest bindings produce explicit declaration conflicts with no selected winner. Harmless
additional capabilities or target declarations remain admissible.

The candidate's actual target content is evaluated independently of the declaration comparison.
A changed target with an unchanged declaration remains `PRESENT_DRIFTED_REVIEW`; a rewritten
declaration also creates a conflict. The audit does not infer semantic loss from different bytes.
`--require-no-missing` exits 3 for missing targets **or** declaration conflicts. Malformed inputs,
unreadable objects or unstable refs refuse with exit 2. A successful read with body drift alone
retains the existing review behavior.

An explicit baseline with an absent, empty or unreadable catalogue refuses. An existing baseline
catalogue whose manifest is missing, empty or malformed also refuses. Only an implicit direct
parent may lack the catalogue; its exact ID and `ABSENT_IMPLICIT_PARENT` observation are recorded
without manufacturing obligations. Explicit strictness wins if a commit is also a direct parent.
This allowance covers history before the catalogue existed; it is not transitive historical coverage.

Baseline reports use schema `m3-retained-capability-baselines/1`. The existing `RETENTION.tsv`
columns remain unchanged; rows represent distinct capability/manifest/path/hash obligations.
`targets` counts those obligation variants, while `distinct_target_paths` counts paths. `SUMMARY.json`
records baseline identities, the absent-parent observations, obligation provenance and declaration
conflicts. The root covers the full deterministic report, including rows. Opt-in declaration reads
require regular Git blob modes and canonical text paths and accept exactly 64 lowercase hexadecimal
SHA-256 characters. The legacy path's parsing and file-mode behavior remain unchanged.

Examples:

```sh
python3 -B m3/history/retention.py --repo /absolute/full-clone \
  --commit <full-candidate-id> --include-parents \
  --baseline-commit <full-base-id> --baseline-commit <another-full-baseline-id> \
  --require-no-missing --output /outside-worktree/retention

mvn -B -f m3/history/retention-pom.xml verify \
  -Dm3.repo=/absolute/full-clone -Dm3.retentionCommit=<full-candidate-id> \
  -Dm3.retentionBaseline=<full-base-id> -Dm3.output=/outside-worktree/retention
```

The existing Maven entry point opts into all direct parents. Supplying `m3.retentionBaseline`
activates a profile that appends one structured baseline argument; omitting the property adds none.
The CLI accepts repeatable baseline arguments for multiple independent pins. Maven's test and audit
execution remain separate phases, with their actual execution evidence recorded separately.

The existing workflow audits the immutable PR head against the immutable PR base and all head
parents. Push events also retain the immutable `before` commit, covering catalogue deletion in an
earlier commit of the same push. The all-zero branch-creation `before` sentinel adds no explicit
baseline; all direct parents are still inspected and the reduced scope is printed. Manual dispatch
accepts an optional exact `retention_baseline` input. Its omission is reported as parent-only scope.
Pins are validated and passed through a Bash argument array, without evaluating them as shell code.
The workflow watches `m3/**`, `src/**`, `test/**` and its own path, so retained receiving documentation,
tests and task evidence are included in its trigger scope.

This workflow is repository-owned audit wiring. Its presence does not establish branch protection,
trusted execution of a candidate-modifiable workflow, whole-repository completeness, a JVM build,
JNI/runtime correctness or acceptance of any retained capability. Those independent M3JDK21 gates
remain with their existing owners. Retiring or replacing inherited obligations needs a separately
reviewed contract transition; this extension does not implement a waiver or retirement mode.

## Recovery/patternization order

Read `ATOM_PLAN.tsv`. First establish the exact candidate/target contract and
restore the *evidence and recipe custody* through a reviewed proposal. Then
reconcile storage admission, ownership/lifetime, UTF-16 ranges, composition,
precomputed facts, Java operation bridges and the coordinated VM/JNI boundaries.
The String layout and its VM consumers form one coupled promotion boundary,
not independent file-level merges. Keep the mapped-kernel/shadow-route work and
the prefix/migration work as separate candidates; do not overwrite newer work.

Use existing exact-source/OpenRewrite recipes for transformations. Every proposed
atom needs a stable name, input/output/effect/exception/concurrency/resource
contract, pattern participant role, source lineage, tests and exact-head receipt.
Unknown semantics remain typed residue. Hash equality is byte identity, not a
proof of behavioral equivalence. Do not add foreign annotation dependencies to
java.base simply to label patterns; use this ledger/Javadoc first.

No blind cherry-pick, blanket revert, current/incoming/both text concatenation,
ancestry-only 'superset' acceptance, or replacement String.class is authorized.
