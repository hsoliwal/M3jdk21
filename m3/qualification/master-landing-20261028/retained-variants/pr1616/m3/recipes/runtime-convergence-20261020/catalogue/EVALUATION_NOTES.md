## Collection findings and provider contracts

Six collection implementation owners are proposed:

- `M3LongIndexProjection`: reversing the order of equal-value runs preserves occurrence stability. A known opposite sorted direction uses O(n) work and one final index array. Unordered sorting retains O(n log n) work and O(n) scratch. This is a complexity result, not a measured end-to-end gain.
- `M3IndexMaskCompactor.java`: existing checked whole/window callers share private stable int/long emission. Validation order, all-selected detached copies, signed extremes, duplicates and native-required refusal remain authoritative.
- `m3_index_mask_compactor.c`: existing checked primitive selectors share emission and avoid reading payload chunks with no selected rows. No Java object references cross JNI.
- `M3FilteredNavigableSet` and `M3FilteredViews`: strict read-only `removeFirst`/`removeLast` refusal applies even to empty filtered views. Sorted reversal remains backed by the original provider, retaining comparator, null, predicate and liveness semantics.
- `M3FilteredLists`: ordinary cursor invalidation repair passes the original donor witnesses, but review exposed exhausted/bounded/empty-sublist generation cases. The seven-test provider fixture had three failures before the fix and now passes all seven on the same fixture. The stable fix is **FIX_VALIDATED_REVIEW_PENDING** until the independent reviewer recheck and final recipe/source seals are complete.

Provider policy must remain explicit. ArrayList/LinkedList cursors preserve their original generation checks. An exhausted bounded iterator may refuse traversal before checking generation; empty providers require separate insertion validation. CopyOnWriteArrayList can be writable while exposing an unmodifiable snapshot iterator: that iterator does not make the backing List immutable. Arrays.asList permits `set` while refusing structural insertion/removal. Truly unmodifiable providers still refuse. Predicate acceptance, exception identity and write timing stay with the existing owner; no generic “all filtered views are mutable/read-only/fail-fast” policy is introduced. M3MutableFilteredViews, deque, collection-composition and sorted-view siblings remain unchanged and held to their own contracts. JDK, Guava, Eclipse Collections, Apache Commons and Spring interfaces are not interchangeable.
