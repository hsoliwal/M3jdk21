# M3 signed-long order-statistics lane (receiver)

This addition is **independent** of `java.lang.String`, `java.util.Collection`, and HotSpot. It does not modify existing Java/JNI signatures. The live M3 filtered and sorted views remain canonical for backed operations; `M3LongRankIndex` is an explicitly immutable, separately captured projection when repeated indexed queries justify precompute.

## Recipe-first ownership

Maven recipe owner: `m3/collections/recipe/order-statistics`. Its five templates are source authority and carry SHA-256 assertions inside `M3RankIndexRecipe`. The product `.java`/`.c` and test files are generated bytes, not sources to hand-edit. For a change, edit the template, update the pinned template digest, run `--apply` on a fresh target or regenerate the existing outputs from the recipe, compile and retest. The strict installer refuses an unexpected divergent postimage rather than overwriting code.

- `mvn -B -f m3/collections/recipe/order-statistics/pom.xml verify` — validate that product files match source-sealed recipe.
- `mvn -B -f m3/collections/recipe/order-statistics/pom.xml compile` then `java -cp m3/collections/recipe/order-statistics/target/classes com.m3.recipe.M3RankIndexRecipe --check .` — direct replay.
- `java -cp ... com.m3.recipe.M3RankIndexRecipe --apply .` — first-time install only; fail closed on existing changed product files.
- `javac --release 21 -Xlint:all -Werror -d /tmp/m3-rank-test m3/collections/src/main/java/com/m3/collections/{M3LongIterator,M3LongCollection,M3LongRankIndex,M3LongRankBatchNative}.java m3/collections/src/test/java/com/m3/collections/M3LongRankIndexSelfTest.java && java -cp /tmp/m3-rank-test com.m3.collections.M3LongRankIndexSelfTest` — JDK-only stand-alone verification (the real module can also compile/test these classes using Maven).

The root `m3/pom.xml` already includes the `m3/collections` module under `m3-extended`; no default-JDK module dependency is introduced.

## Contract and cost profile

| Operation | Baseline arbitrary M3 collection | Immutable precompute index |
|---|---|---|
| Capture | no new index | One cursor, O(n log n) primitive sort, O(n) retained long[] |
| Contains | O(n) for list or backing-specific | O(log n), no boxing |
| Count duplicate keys | O(n) scan | Two binary bounds, O(log n) |
| Signed rank / select | O(n) scan or sorting | rank O(log n), positional select O(1) |
| Value range count | O(n) scan | Two binary bounds, O(log n) |
| Batch lower bounds | O(q n) scan | O(q log n), optional single JNI crossing |

The original source is never modified; no original array or cursor is retained, and capture does not call `source.size()` or `source.toArray()`. Selection preserves duplicate occurrences by default. The opt-in distinct projection compacts adjacent equals once after sorting; dense descending rank is explicitly supported only for a distinct index. `Long.MIN_VALUE`/`Long.MAX_VALUE` are handled without `value + 1`, unsigned arithmetic, or sentinel keys. `toArray()` returns a clone; future source mutations do not alter a snapshot. No claim is made that building an index is faster than direct scans for one-shot queries.

**JNI boundary:** native source is original Apache-2.0 C, an optional `m3rankbatch` library, invoked only after `-Dm3.collections.rank.native=true` and a batch of at least 64 queries. On library absence Java is the correctness fallback. The JNI implementation uses region-safe primitive array handles, returns exact signed-long lower bounds, and never exposes or retains object addresses. No ABI change is made to existing JNI libraries, and no native path is enabled by default.

A local Linux JNI diagnostic build can use:

```sh
JAVA_HOME=$(dirname "$(dirname "$(readlink -f "$(command -v javac)")")")
cc -std=c11 -Wall -Wextra -Werror -fPIC -shared \
  -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" \
  m3/collections/src/main/native/collections/m3_long_rank_batch_jni.c \
  -o /tmp/libm3rankbatch.so
java -Dm3.collections.rank.native=true -Djava.library.path=/tmp \
  -cp /tmp/m3-rank-test com.m3.collections.M3LongRankIndexSelfTest
```

## Algorithm catalogue and donor admission

`m3/collections/algorithm-catalog/order-statistics.tsv` is the searchable decision ledger. It records problem category, suitable reference, baseline, selected algorithm, complexity, contract compatibility, license/copy status and rationale. References to LeetCode, HackerRank, GeeksforGeeks and Apache Commons Collections are **ideas/problem definitions**, not copied submission/source implementations. This source is an independent implementation using JDK `Arrays.sort` and straightforward half-open binary searches. No third-party code, test inputs, binaries or dictionary payloads were imported.

## Evidence / boundaries

- Java 21 `javac --release 21 -Xlint:all -Werror` and 2,500 randomized cases against sorted arrays, `TreeSet` and linear counts.
- C `gcc -std=c11 -Wall -Wextra -Werror` and the same Java differential test with the JNI lane explicitly enabled.
- Invalid ranges throw before any mutation (the index itself is immutable).
- Concurrent structural changes to an input collection during capture are unsupported and follow that input's cursor contract; the index itself is safe to read concurrently after construction.
- No JDK build, HotSpot memory layout, GC reference counting, or java.lang.String replacement is claimed by this isolated increment.
