# M3 array AVL sorted bulk loading

An empty, eager, ascending M3TreeMap owner now copies a compatible SortedMap by reading its ordered entries into Object[] payloads, int[] links and byte[] heights. The existing AVL rotations, deletion and views remain in use. No entry nodes are stored by this path; input Map.Entry objects are API projections.

The private builder adapts fastutil's Apache-2.0 readTree subtree split. See FOSS_REUSE_DECISION.tsv, THIRD_PARTY_NOTICES.md and LICENSE.fastutil. Other inputs and bounded/descending, nonempty, lazy and key-only maps retain the existing per-mapping insertion path. The package-private dispatch hook preserves the existing javac public access bridge.

Qualification used Java 21.0.9. All 130 selected Java sources, including module-info.java, compiled with --release 21 -g -proc:none -Xlint:all,-module -Werror. The two changed owners' class files match those used by the behavior proof. Public inherited method/constructor signatures, generic metadata, bridges, defaults and annotations compare exactly with the pinned baseline.

The independently written public-API proof passed 113 scenarios and 257,312 checks, including 1,873 invariant checks. Its expected-observation digest matches the original JDK run frozen before candidate execution. It covers boundary sizes, natural/reverse/null-friendly ordering, comparator-gated sorted copies, later mutations, source/destination ranges, ordinary sources and explicit lazy values. The ancillary LinkedHashMap check passed; M3HashMap was unavailable in the selected runtime, so no pass is claimed for that name.

To reproduce, use CORE_SOURCE_PINS.json to verify and select the 130 repository Java source paths, then compile them with the flags above into a fresh scratch core directory. Compile M3TreeMapSortedBulkProof.java and TreeBulkPublicApi.java separately with Java 21 into a proof directory. Run M3TreeMapSortedBulkProof with argument oracle using only the proof directory on the classpath, retain its expectedSHA256, then run it with argument com.m3.collections.M3TreeMap using proof plus the newly built core on the classpath. Compare expectedSHA256; positive comparator call counts and diagnostic forEach dispatch counts are not equality assertions. TreeBulkPublicApi prints the public signature snapshot; comparing baseline-first and candidate-first classpaths qualifies metadata separately.

apply_recipe.py exposes transform(raw, name="M3TreeMap" or "M3SlotMap", reverse=False). Apply M3SlotMap first, then M3TreeMap; reverse that order for inversion. The first stage adds the default-false hook and compiles against the unchanged TreeMap body with identical public metadata. Compile both final files together after the second stage. Dictionary order is not the application order. The recipe accepts exact before/after Git blob identities, refuses stale inputs, is idempotent and supports exact inversion. It performs no filesystem writes on import.

This qualifies the sorted bulk-load atom. Full Eclipse TreeSortedMap ownership/serialization, every five-library collection contract, complete Maven/hosted CI and native CRUD remain separate work. No throughput measurement or all-library performance claim is made.
