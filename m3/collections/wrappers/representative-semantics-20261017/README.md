## Defect, atomic change, and compatibility
Prior `M3CollectionViews.FilteredCollection.contains(probe)` evaluates the filter on the *external equal probe* rather than on a stored representative. `remove(probe)` delegates to the backing collection's equality-based removal and can remove an earlier **hidden equal element** instead of the visible occurrence. This is demonstrably incorrect when `equals` compares a business key and the filter uses an independent property. The baseline fails the new standalone oracle.

One sealed, per-file source transformation replaces only `contains`, `remove`, and their contract comment. The candidate finds the stored equal occurrence and tests its visibility. For Lists, removal uses the physical index so a hidden duplicate survives, including when iterator removal is unsupported (CopyOnWriteArrayList). For other Collections, it removes through the backing iterator and conservatively rejects an unsafe fallback; Set's uniqueness admits direct fallback. SortedSet/NavigableSet specialized comparator-aware implementations remain unchanged. No public method/descriptor change and no copied per-element payload store. Stable/pure predicates and external synchronization remain the caller's responsibility.

**Tradeoff:** generic Collection membership is now O(n) (O(1) temporary space), because the public Collection API offers no representative-returning lookup. Previously some owners could do O(1) expected membership but incorrectly evaluate predicate on probes. Do not claim throughput improvement.
