# M3JDK21 filtered/sorted cross-family oracle

This is a **test-only, additive** receiving increment stacked on M3JDK21 #1050.
Production owners remain `M3CollectionViews`, `M3FilteredMaps`, `M3TreeSet` and
`M3TreeMap`. No independent wrapper hierarchy, `java.base` edit, native predicate
ABI, runtime Synexia dependency or collection-phase promotion is introduced.

## Recipe first, inventory first

Reusable source authority remains in Synexia: collection erased-capability PR #11913
and filtered-map composition PR #11920, with their existing Maven/OpenRewrite recipes.
This receiving proof reuses the target's existing source-sealed
`M3HashPinnedJavaSnapshotRecipe` provider, from the pinned
`m3/collections/wrappers/recipe` Maven reactor. The named declarative recipe
`com.synexia.m3jdk.FilteredCrossFamilyOracle20261017` adds **one Java test file**
with `ABSENT` preimage and pinned SHA-256 postimage. Java LST execution, fixed point,
drift refusal, provider contract, and artifact equality must be verified before
using an emitted output; do not patch generated bytes. There is no production source
mutation in this increment.

## Four Java 21 acceptance methods

- Runtime `Collection` erasure preserves actual `NavigableSet`, with live
  range/descending mutations and hidden-member survival.
- Comparator-equivalent query keys use actual stored representatives; filtered
  `NavigableMap` entries are guarded. JDK checked/unmodifiable wrappers compose.
- 192 seeded additions/removals compare exact lower/floor/ceiling/higher, membership,
  ordered entries and values against independently rebuilt TreeSet/TreeMap oracles.
- Existing M3 packed tree owners participate; `sortedSnapshot` is independent
  storage rather than an accidentally live view.

Comparator-inconsistent predicates are used only where the contract explicitly
requires the stored representative, not as an assertion that equality/order conflict
can be silently resolved for arbitrary providers. Predicates are pure and stable.

## Evidence limits

Run the real source-backed Maven recipe and owning test module on Java 21:

```sh
mvn -B -ntp -f m3/collections/wrappers/recipe/pom.xml -Dtest=M3CrossFamilyOracleRecipeTest test
mvn -B -ntp -f m3/collections/pom.xml -Dtest=M3FilteredCrossFamilyOracleTest test
```

The narrow CI gate also checks source/template byte identity and its SHA-256 manifest.
These are separate qualification stages: source seal does not establish behavior,
and four JUnit methods do not prove all JDK contracts, all provider/runtime states,
JNI equality, serialization, concurrency linearizability or memory-performance
improvement. Prior M3 JNI cardinality/run probes remain unchanged. Arbitrary Java
predicates and comparator callbacks stay in Java; no unsupported JNI counterpart
is created.

`AGENTS.md` and the canonical receiving invariant still place the global phase
in **STRING**. This is isolated collection acceptance evidence, not promotion of
`java.util` collection implementations or a full M3JDK image.

## Canonical source pin and mirror rule

The exact reusable recipe and test are now committed in **Synexia PR #12043**,
commit `e05e3adedb2579319355678e7712ec3792bc0863`.
The four Maven/OpenRewrite inputs below are a byte-identical proof mirror,
not a second canonical recipe implementation. Every target mirror SHA-256 and
Git blob matches the immutable Synexia revision; see `SYNEXIA_PIN.tsv`.
The source-sealed JUnit fixture was emitted into this branch before the
canonical resource was pinned. The same reviewed bytes are now canonical
in Synexia, so future improvements must change the canonical recipe first.

The repository's cross-repository access is deliberately not assumed by CI:
the public target verifies the pinned source bytes locally, while the private
Synexia reactor independently compiles/tests the named recipe. No target
workflow may claim remote canonical execution merely because a pin matches.
