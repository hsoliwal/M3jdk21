# Five-provider array/count/flag qualification

The implementation adds a shared M3 primitive count/flag owner, four counted-provider facades, bimaps, M3 multivalue inversion and nine new collectors. The received surface has 33 factory signatures and 20 collectors, preserving all 22 preexisting factories and 11 collectors on the frozen base.

`QUALIFICATION.json` records the exact boundaries and executed gates. `recipe/` contains the five real OpenRewrite SDK test results, complete source-input identities, 42 output identities and actual diffs. `received-core/` retains 211-test core,34-case source-admission and checked Java/JNI evidence. `received-interop/` retains all nine actual provider XML reports totaling126 Jupiter tests, the nested3518 official Guava cases,192 binding checks, public API census, packaged-resource byte checks and23 dependency JAR identities. The two historical recipe directories retain their6 and4 tests respectively, with the original assertions intact.

The final CI successor changes only the retained SDK workflow. All236 core source files,11 core build inputs and24 Java postimages were compared with the actual execution receipts and remain identical. The target publication parent has the same complete tree as frozen base f3c61569. The exact canonical commit and source/engine mirrors are pinned in `../../recipe/five-provider-array-interop-20261017/CANONICAL_SOURCE.json`.

The diagnostic cost report is deliberately unfiltered. It reports cumulative allocation during growth rather than retained heap. M3 construction was slower and allocated more cumulatively in that run; existing-key count updates allocated zero bytes for M3 and all three donor count owners. No whole-library compatibility, full installed JDK image or universal performance claim follows from these gates.
