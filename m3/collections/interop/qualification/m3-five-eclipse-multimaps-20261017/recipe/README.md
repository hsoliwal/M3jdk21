# Five-library M3 Collections SDK — real Eclipse rich multimaps

Canonical Synexia OpenRewrite recipe: `com.synexia.m3.FiveLibraryEclipseMultimaps20261017`. Public product: `hsoliwal/M3jdk21`, optional `m3/collections/interop` Maven module. This is a **source implementation, not merely a catalogue**: adds two real Eclipse Collections 11.1.0 provider classes and four tests (2 seeded oracles, JUnit adapter and one five-vendor integration JUnit).

## Canonical M3 storage — not another collection engine
- `M3EclipseListMultimap<K,V>` implements `org.eclipse.collections.api.multimap.list.MutableListMultimap` by extending Eclipse's abstract rich-behavior owner. The key directory uses `MapAdapter.adapt(new M3LinkedHashMap<>())`; each value group uses `ListAdapter.adapt(new M3LinkedList<>())`.
- `M3EclipseSetMultimap<K,V>` implements `org.eclipse.collections.api.multimap.set.MutableSetMultimap` through Eclipse's abstract set-multimap behavior, `M3LinkedHashMap` keys and `M3LinkedHashSet` value groups.
- No second M3 key-index, array/mask engine or retained per-occurrence M3 Entry/Node. One actual M3 value collection per key, provider-required facade/view instances possible. Some derived operations (list flip to a bag multimap) explicitly use Eclipse result storage; **not universal M3-exclusive storage nor zero-allocation**.
- Key hashing/ordering comes from existing owners; set duplicates and list duplicates are different semantics. Eclipse absent-key `get` returns an unmodifiable empty list, unlike Guava's mutable live absent-key view.
- No new JNI symbol. The independent `M3IndexMaskCompactor` / `M3IndexPathMasks` JNI primitive indices/masks remain the JNI boundary. Java reference payloads, comparators and arbitrary callbacks stay in Java.

## Five correct upstream names (not interchangeable)
See `FIVE_PROVIDER_OWNERS.tsv`: JDK `java.util.Map<K,List<V>>` has key count, Guava `ListMultimap<K,V>` and Apache Commons `ListValuedMap<K,V>` count value occurrences, Spring `MultiValueMap<K,V>` extends Map-of-lists and counts keys, and Eclipse `MutableListMultimap<K,V>` has its own rich methods, absence and derived-value semantics. A single M3 storage family supports distinct API adapters; this does **not** mean all APIs or concrete classes in five upstream libraries are implemented or substitutable.
