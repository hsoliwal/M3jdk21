# M3JDK21 five-provider counted bag and class-map implementation

This first-party Apache-2.0 canonical Synexia recipe adds genuinely new **M3-owned runtime collection types** to the optional `com.m3.collections.interop` product, without renaming vendor APIs.

- **Eclipse Collections 11.1.0**: `M3EclipseBag<E>` implements `org.eclipse.collections.api.bag.MutableBag<E>` by extending upstream `AbstractMutableBag`; one `M3LinkedHashMap<E,Integer>` owns counts per distinct key in parallel array/index slots. No retained element occurrence nodes. Checked 32-bit counts, nulls, multiplicities, counted iteration, key views, selective and groupBy operations.
- **Eclipse Collections 11.1.0**: `M3EclipseBagMultimap<K,V>` implements `org.eclipse.collections.api.multimap.bag.MutableBagMultimap<K,V>`; distinct key directory is the existing M3LinkedHashMap via Eclipse MapAdapter, and each key owns a new M3EclipseBag. Official Eclipse AbstractMutableBagMultimap owns provider behavior, not a copied implementation. Some derived groupBy results are Eclipse provider-owned, and API-facing iterators allocate.
- **Guava 33.4.8-jre**: `M3GuavaClassToInstanceMaps.create()` returns real `com.google.common.collect.ClassToInstanceMap<B>`. Guava's `MutableClassToInstanceMap` contributes its checked behavioral facade and M3LinkedHashMap owns the actual object keys/values. This is a source-compatible API factory, not Guava concrete-class or serialized-form identity.
- **JDK, Spring and Apache**: existing M3JDK21 `M3LibraryCollections` typed factories and their M3 backing owners are **reused unchanged**. `M3FiveProviderBagContractTest` exercises all five real provider JARs, verifying intentionally different sizes/absent views; the Apache 4.5.0 binary is not locally cached so this exact integration test is a required hosted gate.
- No new C/JNI function or ABI. Existing `M3IndexMaskCompactor` remains the native primitive-mask boundary; ordinary provider object contracts remain in Java.

## Mandatory recipe-first generation
Named OpenRewrite recipe `com.synexia.m3.FiveProviderCountedBags20261017` reuses existing `M3HashPinnedJavaSnapshotRecipe` in actual Java LST (not PlainText) mode. Eight ABSENT-before production/test sources have exact SHA-256 postimages and fixed point. A wrong output requires fixing this source template/recipe and regenerating. Source-first branch records templates, tests, catalogue, proof and vendor license/provenance. No manual patching of generated production output.

On Linux OpenJDK21.0.12.1 against **real Guava 33.4.8-jre and Eclipse Collections 11.1.0 JARs**, strict `javac --release 21 -proc:none -Xlint:all -Werror` passed using the existing compiled 77-core-M3-owner baseline. The real Eclipse binary seeded oracle passed **251,476 checks / 8,300 operations**; Guava passed **11,992 checks / 3,000 operations**; both repeated and passed under `-Xint`. Total **263,468 checks per JVM mode**. Actual local Maven3.9.9/OpenRewrite8.17.1/Jupiter5.10.2 **3 JUnit recipe tests PASS**: eight exact AST outputs, four single-missing partial cases in both input orders (8 partials), fixed point, occupied/duplicate refusal. Real provider proof is bounded; no JMH, heap, zero-allocation, cross-platform or full provider suite claim.

Remaining gates: exact-current M3JDK21 head recompilation, Maven/JUnit of all core & optional interop, authentic Apache 4.5.0 five-provider JUnit, core-JNI C17 `-Xcheck:jni`, installed JDK/jtreg/JCK, GC/JMM/serialization/version permutations, matched CPU/heap benchmarks.
