## Why insertion alone is a credible fit

Current `Tree.balance`379-390 recomputes height, rotates if necessary, and always follows the resulting root's parent. `insert`437-447 attaches a leaf, increments size/revision once, then calls that walk. Preexisting ancestor height fields still describe their subtrees before insertion. An insertion-only refinement can capture an ancestor subtree's old height before recomputation; after any existing single/double rotation, compare that old height against the height of the **resulting subtree root**, not the old rotated-away slot. If unchanged, the subtree presented to its parent has the same height as before insertion: remaining ancestors cannot require height/balance repair. If height grew, continue through the resulting root's parent. The comparison must occur after rotations and their height updates.

This is a source-derived proof obligation, not an executed equivalence result. It assumes the pre-insertion tree already satisfies its height/link invariants; writes/rotations below the stopping point have completed. Search, comparator calls, representative keys, root/parent links, free-list ownership, lazy state admission, structural revision and existing rotation choice must remain untouched. Duplicate replacement performs no structural insertion and must remain on its existing path. No persistent array/cache/counter or new public method is needed by the selected law; scalar old-height state does not change asymptotic memory.

Worst-case insertion remains O(log n), including search. The opportunity is a smaller constant in bottom-up repair, not a lower search bound or guaranteed end-to-end speedup. Small trees, branch cost, growth, comparator/key costs and JIT decisions can erase or reverse the gain. No implementation has been proved fastest, peak, or allocation-free.

### Deletion must not inherit this guard

Current `erase`449-467 shares `balance`. For a two-child removal it transplants a successor and calls `update(successor)` at462 **before** bottom-up repair. A guard that treats the encountered field as the pre-deletion subtree height can therefore compare against an already changed value and stop too soon. Preserve the current complete deletion walk; an insertion-only dispatch must be explicit. Deletion optimization needs its own old-height/provenance reasoning and frozen transplant/cascade witnesses, not a generic condition inserted into the shared loop.
