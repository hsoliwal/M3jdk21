# M3 invariant — streaming source revalidation after indexed JNI search

## Original owners
Exact original Synexia PR #16607 `9c2288e951a2a1b15afe22d75bec6e473fd18694`. The existing `M3PmemSourceImage` and `PmemGramCampaignAdmission` remain the original owners. Do not create another model caller, native JNI export, byte-index engine, source reader or downstream M3JDK recipe framework.

## Defect and scope
The current reviewed Gram campaign uses `image.readSealed(file)` after a complete indexed search to rehash **all selected files**, including those excluded by the Gram filter. Its return value is immediately discarded. Therefore verification of 20,000 source files averaging 50 KiB allocates approximately 1 GB of short-lived Java byte arrays even though a 32 GB machine already holds the immutable repository in mapped memory.

## One exact source and one campaign atom
- Add a *compatible* `M3PmemSourceImage.verifySealed(int,byte[])` method: read a source in windows through the original `M3PmemRegion.read` Java/JNI lease, update the existing SHA-256 digest incrementally, compare to original `M3PmemSourceSlices.sha256At`; throw `SecurityException` on drift. No file-sized copy survives or escapes. Return source byte length.
- Require a nonempty bounded **caller-owned** scratch buffer. Serial callers reuse the same 16 KiB window. Even empty files perform an original zero-length region read, preserving close/lease preconditions.
- Change only the post-search full-selected-file verification loop in `PmemGramCampaignAdmission` to allocate one reusable scratch buffer. Source-generation error/cancellation, preflight/reviewer order, exact JNI/FILE KMP results, complete search gate, SHA roots, LLD context, donor taxonomy, durable one-call ledger and **all existing public method descriptors** remain unchanged (one compatible public SDK method is added).
- No source/text normalization, no third-party runtime dependency, no vendor challenge/editorial source copied, no change to C17 JNI headers. A full source read and SHA check is still required; no wall-clock performance claim is made.

## Proof and HOLD
New source-sealed JUnit checks FILE-backed exact digest, small 7-byte/1KiB scratch crossing window boundaries, binary and zero-length source, out-of-bounds and empty/oversized scratch refusal, same-length external backing mutation refusal, closed-file behavior and opt-in real POSIX JNI parity. The original reviewed campaign JUnit still runs.

Canonical `M3HashPinnedJavaSnapshotRecipe` has exactly 2 PRE→POST Java targets and 1 ABSENT→POST JUnit target. Actual Maven/OpenRewrite typed `Recipe.run`, exact first-pass generated bytes, fixed point and refusal tests are authored, **NOT RUN** until original full-repository Maven/JUnit checkout is available. Existing native/JMOD, provenance, 1GiB physical RSS/throughput, live Chrome on-device model and every downstream `hsoliwal/*` product gate are HOLD. Preserve NRD/no force-push.
