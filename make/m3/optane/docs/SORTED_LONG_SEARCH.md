# PMEMSDK sorted-long index search (v0.5)

## API and semantics

- `lowerBoundLongLE(region, byteOffset, elementCount, key)` returns the first
  **element index** in `[0, elementCount]` whose signed int64 value is `>= key`.
- `upperBoundLongLE(...)` returns the first index with value `> key`.
- The input must be ascending in **signed Java long** order. Duplicate keys
  are supported; empty ranges return 0. A byte offset can be unaligned.
- `byteOffset` is relative to the mapped region. A returned element index
  is **not** a file or byte offset. For element `i`, the corresponding mapped
  byte address is `byteOffset + 8*i`, after bounds checks.
- Each value must be encoded little-endian, independent of host endian.
  The native kernel decodes bytes individually and transforms the sign bit
  for an exact unsigned ordering comparison; it performs no unaligned load.
- Both Java and JNI reject negative offsets/counts, `elementCount*8`
  overflow and out-of-range spans. One Java read lease remains held over the
  entire native binary search, preventing same-owner close/write races.
- Native execution takes `O(log elementCount)` comparisons and `O(1)`
  auxiliary memory. There is no Java `byte[]` staging per query.

## Example

```java
long first = PmemSearch.lowerBoundLongLE(region, 7L, 1024L, 42L);
long after = PmemSearch.upperBoundLongLE(region, 7L, 1024L, 42L);
// The equal-key run is [first, after), in *elements*.
```

## Verification

`PmemSortedLongSearchSmokeTest` compares the JNI implementation with a
linear, independent Java reference over 700 seeded random sorted arrays,
negative values, duplicate boundaries, empty arrays and signed extrema. It
includes a sparse file mapping at an absolute offset greater than 2 GiB,
invalid ranges and use-after-close rejection.

The atom registry adds separate JUnit 5 correctness + performance tests for
both methods, generated by `PmemAtomJUnitRecipe`. Tests also run without
JUnit via `PmemAtomCases`. The synthetic `ns/op` output is a smoke workload,
not a comparative latency or throughput claim.

## Donor/category decisions

LeetCode 35 establishes search-insertion semantics; HackerRank Climbing
the Leaderboard demonstrates sorting/indexing use cases but uses a different
ranking contract; GeeksforGeeks Lower/Upper Bound defines duplicate semantics.
The binary search here is independently authored for the 64-bit mapped
file constraints; no contest submission code is copied.

No actual Optane/PMDK/DAX or dual-Xeon locality has been tested. External
processes modifying/truncating the file can invalidate both sorted order and
a mapped page; model/index owners must enforce external file immutability.
